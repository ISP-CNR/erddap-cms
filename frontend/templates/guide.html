How to add a new dataset

A short walkthrough of the whole process, from uploading a file to seeing the dataset live on ERDDAP.

{% macro step(num, title, step_id) %}
{{ num }}. {{ title }}
{{ caller() }}
{% endmacro %} {% call step(1, "Start the upload", "1") %}

Click Add new dataset (top right of the dataset list), then choose:

  • From existing file - the common case, covered below.
  • From another ERDDAP - paste the URL of a dataset already published on a different ERDDAP instance to pull in its existing definition, instead of starting from a raw data file.
{% endcall %} {% call step(2, "Upload a file", "2") %}

A dataset is built from one or more data files in .csv, .nc (NetCDF-3) or .h5 (HDF5) format. Upload one file to start - you can add more to the same dataset later.

  • Dates/times in a CSV file must use the format yyyy-MM-ddTHH:mm:ssZ.
  • NetCDF/HDF5 files that already carry proper metadata (COARDS/CF/ACDD conventions) need the least manual work afterwards, since the CMS reads titles, variable names and attributes straight from the file.
  • A CSV file has no way to carry a title or summary, so the form asks for those directly when it detects one.
{% endcall %} {% call step(3, "Pick the dataset type", "3") %}

This tells ERDDAP how to interpret the file's rows/dimensions, and hover each option for its full description:

  • Time Series - repeated measurements over time at a fixed latitude/longitude/depth.
  • Time Series Profile - repeated profiles (multiple depths/altitudes) over time at a fixed location.
  • Grid - gridded data (e.g. satellite imagery, model output) with regular latitude/longitude/time axes.
  • Other - no requirements; use this if the dataset doesn't have latitude, longitude and time variables, or doesn't fit the other options.

The common case is the simplest one: one file, one station, a single fixed latitude/longitude for the whole dataset - if that's your data, there's nothing extra to do. If the file has no station column at all, the CMS adds one for you automatically (a station_id variable, visible on the edit page's Simple form) and treats the whole file as one single station.

"Fixed location" is per station, not per dataset, though - a single Time Series (or Time Series Profile) dataset can hold data from many different stations, as long as the file has a column identifying which station each row belongs to, like in this example CSV (3 stations, 3 rows each - same latitude/longitude repeated for every row of the same station).

For a CSV, the CMS decides which column identifies the station by its name: any column containing "station" (e.g. Station_ID). If your station column isn't picked up, the fix is simple: rename it to include "station" and re-upload .

A NetCDF file gets an extra, more reliable path: if it already declares cf_role="timeseries_id" on some variable natively - whatever it's named, e.g. platform_id - the CMS uses that directly; the name-matching rule above is only a fallback for when the file doesn't declare it already. Likewise, if the file already declares a supported CF featureType, the CMS trusts that over whatever dataset type is picked here. Two matching example NetCDF files (same 3-station data as the CSV above) - both validate cleanly on ERDDAP:

  • without cf_role - a plain station_id variable, picked up by name.
  • with cf_role - a platform_id variable that already declares cf_role="timeseries_id", picked up by attribute despite the non-matching name.
{% endcall %} {% call step(4, "Fill in the initial fields", "4") %}

A handful of fields are asked for up front:

  • Title / Summary - only asked for CSV files, which can't carry them internally.
  • Creator email - defaults to your own account email.
  • Info URL - a web page with more information about the dataset or your institution.
  • Institution - start typing to search; results come from ROR, the public registry of research organizations.
  • Latitude / Longitude - only shown if the file doesn't already contain valid coordinates.

Click Ok - the CMS reads the file, auto-generates a first draft of the dataset's full metadata (variables, data types, attributes) and creates the dataset. You'll land back on the dataset list, where the new dataset now appears with Validated and Published - that's expected, the next steps finish the job.

{% endcall %} {% call step(5, "Finish the metadata", "5") %}

Open the new dataset: click its icon in the Actions column (not its name - that links to ERDDAP itself) to reach its edit page. Fields marked with * are required - things like institution, summary, history, Conventions, license, creator_name/ creator_email, contributor_name/contributor_email/ contributor_institution and standard_name_vocabulary. Most are pre-filled with reasonable defaults - check them rather than assuming they're right for this dataset.

Each variable also has a couple of descriptive attributes worth checking:

  • long_name - free text, whatever human-readable label you want (e.g. "Sea Water Temperature"). Shown as-is in plots and other tools.
  • standard_name - not free text: it's a fixed, machine-readable term from a controlled vocabulary, so other tools can recognize e.g. "this column is sea water temperature" automatically. Start typing in the field to search it - the CMS bundles the CF v1.6 standard names table, so only terms from that list are offered, and only variables that actually have a matching one need it filled in. It's not strictly required, but worth doing where one applies.
{% endcall %} {% call step(6, "Private dataset? (optional)", "6") %}

If the data shouldn't be publicly downloadable yet (e.g. under embargo), toggle Private dataset on the edit page before publishing - the title, summary and graphs stay visible to everyone on ERDDAP, only the raw data requires a login. This can be changed at any time later.

{% endcall %} {% call step(7, "Save, Validate, Publish", "7") %}

Same three steps for every change, new dataset or not:

  1. Save your changes.
  2. Validate them - ERDDAP checks the metadata is correct. Fix anything it flags and validate again.
  3. Publish (or Reload, once already published) to make it live on ERDDAP.

Once Enabled, Validated and Published are all green, the dataset is live and reachable on ERDDAP.

A brand new dataset starts out disabled, and only an admin can flip the "Enable dataset" switch - so Published will stay red no matter how many times a non-admin clicks Publish, until an admin enables it. Ask an admin to enable your new dataset once it's validated.
